# Research engine web app

The browser front end of the research engine. It talks to [research-api](../../packages/research-api/README.md) and nothing else, and it runs on your own machines: no analytics, no third-party scripts, no hosted fonts.

It has the build, the providers, sign-in and the forced password change, the layout with a status badge, light and dark themes, Spanish and English, the TypeScript client generated from the API's OpenAPI document, and the test and CI setup. The **Circuits** screen is built (see [Circuit check](#circuit-check)) and so are the **Ask** screen (see [The Ask screen](#the-ask-screen)), the **Question sets** screens (see [Question sets](#question-sets)) and the **Benchmarks** screens (see [The Benchmarks screens](#the-benchmarks-screens)). Every screen is built.

## Run it

You need Node 22.22 or later (`.nvmrc` pins Node 24.22.0 for CI) and [pnpm](https://pnpm.io) 12 (`packageManager` in `package.json`). From this folder:

```bash
pnpm install --frozen-lockfile
```

Start the API in fake mode (test data, loopback only) in one terminal and the web app in another:

```bash
# repository root
uv sync --locked && uv run research-api serve --fake       # http://127.0.0.1:8090
# apps/web
pnpm dev                                                   # http://localhost:5173
```

The dev server forwards `/api` to the API (`RESEARCH_API_URL` changes the target), so the browser only talks to its own origin and the API needs no CORS. In production the API serves the built files from the same origin ([The web app](../../packages/research-api/README.md#the-web-app) in its README; [Run the web app on a shared server](../../docs/run-guide.md#run-the-web-app-on-a-shared-server) for the install steps).

The API does not serve sign-in yet, so in development `/login` finds no `/api/v1/auth/*` endpoints. Until the sign-in pull request lands, the screens behind the session cannot be reached by hand; the tests use a mock (see [Sign-in](#sign-in-and-the-mock)).

## The API contract and the generated client

The API's OpenAPI 3.1 document is committed as `src/api/openapi.json` and the types made from it as `src/shared/api/schema.d.ts` (generated, never edited). The `contract` CI job regenerates both and fails on any difference. After a change in `research-api`:

```bash
uv run research-api openapi -o apps/web/src/api/openapi.json
cd apps/web && pnpm gen:api
```

`src/shared/api/client.ts` builds one client with `openapi-fetch` and `openapi-react-query`. Two middlewares run on every call: one adds the `X-CSRF-Token` header (from the `re_csrf` cookie) to writes, the other turns any error response into an `ApiError` (RFC 9457 problem details), so callers handle one error type.

## Sign-in and the mock

The sign-in endpoints (`/auth/login`, `/auth/logout`, `/auth/me`, `/auth/password`) are in the generated types like any other; `src/shared/api/types.ts` gives `Me`, `LoginRequest` and `PasswordChangeRequest` their short names.

`src/test/auth-mock.ts` is a small state machine for those endpoints (two made-up accounts, one of them with a temporary password, a failed-login limit, a CSRF check). The Vitest tests serve it through MSW and the Playwright test through route interception. In the end-to-end smoke test `/status` is answered by the fixture too, because the API gives it to signed-in members only and the mock makes no real session; `/health` comes from the real API in fake mode. Its accounts (`ana`, and `temp` with a temporary password) copy two of the API's seeded test users for fake mode, so the mock and the real API answer to the same names. The mock stays so that most tests need no account state; `e2e/real-api.spec.ts` signs in against the real API in fake mode with no mock (a wrong password, `ana` signing in and out with the status badge, `temp` changing its temporary password). Each of its accounts is used by one test only, because the fake server keeps its accounts until the run ends and a changed password stays changed; so `pnpm e2e` does not reuse an API left running on port 8091 (stop it first), and that file runs with no retry.

## Circuit check

`/circuits` reads a circuit, simulates it and checks it. It uses the generated client for `/circuits/parse`, `run`, `check` and `conventions`, and needs no model server: in fake mode the API runs the real parser and simulator. The four endpoints need a signed-in member, so `e2e/circuits.spec.ts` signs in against the real API as the seeded member `dani`, which no other end-to-end file uses (a test that talks to the API directly gets its own session, with the CSRF header and `Origin` the API checks, from the `api` fixture in `e2e/fixtures.ts`).

| Part        | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Input       | A LaTeX tab (quantikz, Qcircuit, yquant, tikz-cd) and a `circuit/1` JSON tab, ten examples, Ctrl+Enter to read. LaTeX goes to `/circuits/parse`. A `circuit/1` document is read in the browser, and a key written twice is refused there with its name (`strictJson.ts`); the API refuses it too and stays the authority, and the JSON typed by the person is sent as typed, never re-written.                                                                                                                                                                                                                                    |
| Gate list   | The status (`parsed`, `partial`, `unparsed`), one table per circuit and per side of a drawn equality (step, gate, targets, controls, open controls), the wire legends, the gate list in words, and a list of every part the reader did not understand. A block with several circuits offers a choice.                                                                                                                                                                                                                                                                                                                             |
| Simulate    | Input state (basis label or amplitudes), parameter values as `name = value` lines, the unitary as a switch. Shows the amplitudes and a bar list of probabilities (first wire most significant), the unitary (a 16 by 16 corner of a large one, the whole matrix as a download), the measured wires and the notes. A table wider than its card scrolls sideways inside it, in a region a keyboard can focus. Screen readers get one short sentence when a reading or a result arrives (the tables are not live regions). A circuit with a symbol and no value says which names are missing and adds them to the values on a click. |
| Check       | Against a state, a unitary, a second circuit (LaTeX or `circuit/1`) or the equality drawn in the circuit. The verdict is _Equal up to global phase_ or _Not equal_ with the largest deviation, and a table of the comparisons (method, exact, phase).                                                                                                                                                                                                                                                                                                                                                                             |
| Refusals    | A circuit the simulator refuses is a `200` with `status: refused`. The screen shows it as **Refused**, in a different style from _Not equal_, with every reason word for word, and never as a result. A `400`, `413`, `422` or `503` from the API is a separate problem panel with its detail, the field it points at and `Retry-After`.                                                                                                                                                                                                                                                                                          |
| Conventions | A card with the conventions of the last result (or the simulator's own before any), the limits, and the gate table. The screen takes up to 12 wires, or 8 for a unitary or for a comparison of two circuits (the API's caps).                                                                                                                                                                                                                                                                                                                                                                                                     |

State: what was typed, what was read and the last answer are in one Zustand store (`store.ts`), in memory only. Anything that a request depends on clears the answer, so the screen never shows a result for text that is no longer there; an answer that arrives after the circuit text changed is dropped, but a reading survives edits of the options. The three requests (`flows.ts`) go through TanStack mutations, so a `401` sends the person to sign in.

The API passes `quantum-sim-result/1` and `circuit/1` through as open objects, so `types.ts` types them by hand and reads every answer through guards; an answer of another shape is a problem panel, not a crash. `src/features/circuits/fixtures/captured.json` holds 35 real answers of the API (parse, run and check, refusals and errors). The unit tests replay them through MSW (`src/test/circuits-api.ts`; a request with no recording fails the test), and the end-to-end test asks the API for every request again and fails when an answer differs, so the file cannot go stale. After a change in the API or in quantum-sim, start the API in fake mode and run `pnpm capture:circuits http://127.0.0.1:8091`.

## Question sets

The screens of the question sets (`src/features/qsets`) work on the API's `/sets` endpoints, through the generated client. Every rule about what a set may hold is the API's (the `qset/1` JSON Schema, checked by the server); the screens shape the input, show each problem where it belongs and never copy a rule that could drift.

| Route                            | Screen                                                                                                                                                                                 |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/sets`                          | The catalog of every version (status, items, review progress, md5, corpus, owner), a form to start an empty draft or the next version as a copy, and the import of a file              |
| `/sets/:name/:version`           | One version: its md5, review progress, export, and the items in a table that is filtered and paged by the address (`form`, `content`, `lang`, `split`, `tag`, `review`, `q`, `offset`) |
| `/sets/:name/:version/items/:id` | One item: the editor, the review and the decisions so far. A frozen version shows the item read only                                                                                   |
| `/sets/:name/:version/new-item`  | A new item for a draft                                                                                                                                                                 |
| `/sets/:name/:version/freeze`    | What freezing does, by item, and the freeze itself                                                                                                                                     |

**The editor.** The fields follow the form kind: a multi-paper form shows `synthesis` and `necessity`, a circuit form shows `circuit`, `unanswerable` and `multi_list` show the search record, a `circuit_verify` answer is yes or no. Key facts and tags are rows. What has no control of its own (the gold papers, the necessity, the circuit, the search record, and every field that is not listed, such as `choices`, `confusers` or `ext`) is a box of JSON, and a second tab holds the whole item as JSON. While a box cannot be read as JSON, saving, checking and deciding are off, so what the person sees is what is sent. Saving sends the whole item with the `etag` of the draft that was read in `If-Match`; the `422` list is shown at each field by its JSON pointer (the whole-item JSON tab prints the whole pointer), and any problem at a part the form does not show is listed above the form, so none is lost. After a refused save, check, add or delete, focus moves to the first field with a problem, or to the block that explains the refusal; a button that is busy stays focusable (`aria-disabled`) so focus is never dropped. "Check against qset/1" is a dry run (`POST /sets/validate`): nothing is stored. While a box holds text that cannot be read, the view does not change (the text would be lost). Text that cannot be read yet counts as an edit: it is not lost to a read of the item by someone else's change (the merge, "Keep my edits" after a refused save and "Use the latest value" of a merged field wait until the box is fixed, each with a line that says why; "Use the latest value" waits only when the box that shows that field is the broken one; "Load the latest" or "Discard changes" drops it in one click). Leaving the page with unsaved edits (a link, the back button, closing the tab) asks first; signing out from the menu and the redirect to sign-in after a session ends are not stopped, so those edits are still lost then. Text typed while a save is on its way stays in the editor as an unsaved change on top of what the server stored. When the server stores other text than it was sent, only the parts that show a changed field are drawn again, so a tag row just added and a number half typed stay where they are, and focus goes back to the control that had it when its part is drawn again; "Discard changes" is off while a save is on its way. An address that names a page past the end of the list says so and offers the last page.

**Conflicts (the rules of the API that the screens answer).**

- After a merge, a field that both people changed keeps the person's value and Save is on at once: saving it replaces the other value, which the notice listed.
- The editor keeps the item and the `etag` it was built from. Every save, delete and review carries that `etag` (or the newest one, when the item itself has not moved), so a read that lands under unsaved edits never changes what a save overwrites. When the item is read again and the server holds other text: with no edits the editor shows the new text and says which fields changed; with edits it stops and asks, and nothing is saved or decided until the person merges their edits onto the latest version or loads the latest and drops them.
- A `409` on a save says the draft changed since the item was opened. The person loads the latest version (the edits are dropped) or keeps the edits: the item is read again and the edits are merged field by field onto it. Fields only the other person changed come from the server, fields only the person changed stay, and a field both changed keeps the person's value and is listed with both values, with a button to take the other one. A new item has nothing to load, so only "keep my edits" is offered (it reads the draft's `etag` again).
- A `409` of type `item-has-decisions` says the item has review decisions, so its text is fixed. The page leads the person to propose the same changes as an `edit` decision.
- A `409` on a review says the draft changed while the item was open (the `etag` covers the whole draft, so an edit to any item gives every open reviewer one). The item is read again and the note stays. If the item's own text changed, the editor shows the new text with a notice naming the fields (or, when the reviewer has edits, asks them to merge first), so the second decision is about text the reviewer has seen.
- The freeze names the plan that was read (`If-Match` with the plan's `etag`). A `409` says a decision or an item changed: the plan is read again before the freeze can be tried again. The plan page explains what a `stale` decision is: made before the draft last changed, and still applied, because an item with decisions keeps its text.
- A refused import (`422`) lists the lines and fields at fault (the first dozen, and how many more).

**Who sees what.** The owner of a draft and an admin edit it and freeze it. Any member reads, imports, exports and reviews, and another member's page says so instead of offering a save. The API refuses what the page does not offer, and the page shows the refusal in the server's words.

**Export and import.** Export downloads the file exactly as stored, so its md5 is the md5 shown for the version. Import sends the chosen file as the request body (no multipart), for a `qset/1` file or one of the older shapes the API lists.

**Tests.** Vitest covers each screen against recorded answers of the real API (`src/features/qsets/fixtures/captured.json`, made by `pnpm capture:sets`, served by `src/test/sets-api.ts`; an item with no recording is a 404). `e2e/sets.spec.ts` runs the acceptance checks S1 to S5 against the API in fake mode with its seeded accounts, with a private copy of the demo draft for each test that changes something, two browsers for the two-reviewer and conflict cases, axe scans in light and dark, Spanish, a 375 px width and a check that the recorded answers still equal the API's. The demo sets are only read.

## Structure

```text
src/
  app/            router, providers, layout, top bar, error and not-found screens
  features/       one folder per screen: auth, status, ask, benchmarks, qsets and circuits (all built)
  shared/
    api/          generated types, the client, ApiError
    i18n/         es.json, en.json, language detection
    layout/       page heading, placeholder page
    markdown/     Markdown with math for answers and papers
    forms/        labelled text field
    lib/          storage, theme, class-name helper
    stores/       Zustand store for the client-only choices (theme, language)
    ui/           shadcn/ui components (generated)
  api/openapi.json   the committed contract
  test/           test setup, MSW server, the sign-in mock
e2e/              Playwright tests
```

The same rules as the API's import contracts, enforced by ESLint (`no-restricted-imports`):

- A feature never imports another feature or `app`, and stays inside its own folder (no `../`). What two features need goes to `shared`.
- `shared` never imports `features` or `app`.
- Components do not call `fetch`. Only the hooks in `features/*/api.ts` do, through the client.

Server state lives in TanStack Query, client-only choices in Zustand; nothing the server owns goes into a store. Screens are lazy routes, so heavy libraries load only where they are used.

## The Ask screen

`/ask` (`src/features/ask`): a question box, the answer with its sources, and the papers it cites.

- **Sending.** The button or Ctrl+Enter sends; a blank question cannot be sent. `POST /asks` answers `202` and the answer is followed on `GET /asks/{id}/events` with the browser's `EventSource`: queued (with the number of questions ahead), searching the papers, writing the answer, then the answer or an error. The steps are shown in order and announced to a screen reader. One question at a time per tab; it can be cancelled.
- **The answer.** Markdown with LaTeX math (`src/shared/markdown`: react-markdown, remark-math, rehype-katex; raw HTML is shown as the text it was written as and never rendered, only web addresses become links, no image is fetched; a formula wider than its line scrolls inside its own box, which takes the keyboard focus; each formula is measured by itself, so short ones beside it stay plain text). Each citation the answer prints, `(<16 hex> pages 3-4)`, is a button (also each one inside a parenthesis that joins several, `(<key>, <key>)`), and so is each chip under "Sources". The warnings of the engine, the timings and "Edit and ask again" are there too. "What the model read" lists the passages the answering model was given, collapsed until asked for.
- **The paper.** A citation opens a side panel with the paper's title and the cited page as Markdown (`GET /documents/{id}/pages/{n}`), with next and previous page. A LaTeX source says "section N". The citation may name the paper by its full id or by the 16 printed characters; the API completes the short one. Escape or the close button shuts it and focus returns to the citation.
- **Options for one question.** A popover with the three things the API takes per question: search with the index or not, keyword matching (server setting, English, always, never) and completing a cut equation or table (server setting, yes, no). A choice left at "server setting" sends `null`, so the server's own configuration decides. The API does not report that configuration, so the screen cannot print the default values.
- **The engine.** `GET /status` is read every 30 s (every 3 s while the engine starts). A starting engine and one that reports a problem both turn the Ask button off and say why. Only the first clears by itself: an engine that reports a problem is marked ready again by the next question that works (the status is read again the moment an answer arrives, not at the next poll), and `/status` does not probe the model servers yet, so that notice also carries an "Ask anyway" button. Sentences that come from the server (failures, warnings, the reason of an unavailable engine) are shown as the API sends them, in English, whatever the language of the screen. A failure during the ask (`503`, `502`, `422`, `429`) shows the server's message and a "Try again" that sends the same question with the same options.
- **If the connection breaks.** The screen asks `GET /asks/{id}` where the question is: it takes the answer if it is done, opens the stream again if it is not, and says so when the service has forgotten the question (it keeps one for 30 minutes).
- **History.** The last 10 questions of the tab, answers included, live in a Zustand store and nowhere else (no server history, no `localStorage`): the answers hold text of the papers. The store is emptied when the person signs out or the session ends (`src/shared/lib/session.ts`), and a question being answered goes on when the screen is left.

## The Benchmarks screens

Three routes under `src/features/benchmarks`, all behind the sign-in: `/benchmarks` (start a run, the jobs, the runs), `/benchmarks/jobs/:jobId` (one job) and `/benchmarks/compare?runs=a,b&score=s` (results and comparison). The address holds run ids and the id of a score and nothing else: no question text. Everything runs against the API in fake mode (three arms, two models, one of them down), and the live service differs only in what it can do (see the oracle arm below).

- **Start a run** (`RunForm`, react-hook-form with a zod schema in `schemas.ts`). A frozen version of a set (drafts are not listed; each option shows the start of the set's md5 and its number of questions), the arms `bare`, `harness` and `oracle` (the words of the formats, with a sentence next to each), the models of `GET /models` and the repeats (1 to 10). A model whose server does not answer is shown, disabled, with the reason, and cannot be chosen; the list is read again every 30 s and a model that goes down after it was chosen is unchecked and not counted. The API makes one job for each arm and model; the form says how many, and after the start lists the jobs with their state and their place in the line, as the list of jobs has them now. Start, Score and both Resume buttons are guarded against a double click: a second call while the first is in flight gets the first answer and sends no request (`useSingleFlight` in `api.ts`), because a disabled button takes effect only after the next render. A refusal of the server (`409`, `413`, `422`, `429`, `503`) is shown with its own words, `Retry-After` included. **The oracle arm is disabled when `/status` says the service runs live**, with the reason the screen gives (docingest cannot yet answer from given passages: scope PR 0b; the text is the app's own, `form.oracleLive`). The API has no field that says which arms a service can run, so the screen decides from `mode`; a server that still refuses it answers `503` and the screen shows that.
- **Jobs and runs.** The jobs table (newest first, a link to each, the state as a word) and the runs table are read every 2 s while a job is open and every 15 s otherwise. A run still going cannot be picked; a run that stopped early is marked _partial_ with its count. Pick one run for its results or two to compare them: the first picked is the base, the second the variant (the difference is variant minus base), with a button to swap them. Runs of different sets or versions cannot be compared.
- **One job** (`JobPage`). `GET /jobs/{id}` every 2 s until the job is settled (the API's `settled` flag). The state, the answers done out of the total and the place in the line (or the reason it waits) are in a polite live region; a bar shows the share; the time taken ticks every second outside the live region. The log (`LogTail`) is a `log` region a keyboard can focus. It is read from the byte where the last read stopped (`offset`, `X-Log-Next-Offset`) and appended, and read again from 0 if the file got shorter. The API cuts a read at 64 KiB, so a read follows the pages until `X-Log-Next-Offset` reaches `X-Log-Size`. The runner settles a job before it writes its closing lines, so the reading goes on after the job settles, until a read that began then adds nothing. The log is not a live region (the status line above it is). `waiting_for` and the text of a problem are the API's own English words, also on the Spanish screen. **Cancel** asks first (a popover; Escape or "Keep it" leaves the job as it was) and, for a running job, says it stops before the next question; the page shows _Cancelling_ and then _Cancelled_ with the answers so far, and the partial run stays in the table. **Resume** continues from the first answer that is missing; a resumed job waits its turn behind the job that took the lane. Only the owner or an administrator sees the buttons (the API checks too).
- **Results and comparison** (`ComparePage`). Without `score` in the address the screen uses the newest score that holds these runs (and, for two runs, the pair in this order) and was made after the runs last changed (the later of the run's `ended` and the end of the job that made it, with a second of slack because a score writes its time to the second; a run whose job is waiting, running or being cancelled, as after Resume, is changing now, so no score counts as current until the job settles; if the run list cannot be read, the screen says so and offers to try again instead of guessing); a score made before that, for example before a cancelled run was resumed, is not opened: the screen says it exists, offers to open it anyway, and offers to make a new one. An older score opened by its address carries the same notice. If there is none it offers to make one (`ScoreStarter`: base and variant with a swap, and an optional noise pair of two runs of the base's arm). Scoring is a job of the CPU lane; the page follows it like any job and opens the results by itself. A score is kept, so the next visit opens at once. Then: **the summary by group** (mean, 95% interval and n of each chosen metric, for each run; `all`, `lang=es`, `content=math`, categories and so on, as the scorer wrote the groups), **the paired comparison** of two runs (the difference variant minus base, its 95% interval, the questions that went up and down, and the noise floor and whether the difference counts when a noise pair was scored) and **a row for each question** with the chosen metric averaged over the repeats and the keys found and missing, a change column for two runs, a search box and a filter (all, the arms disagree, the variant is better, the variant is worse; the counts agree with the comparison's up and down). The numbers are the API's: nothing is computed again here except the per-question average of the repeats and the "disagree" test, which `GET /scores/{id}/items` supports and the API has no filter for. They are written with up to four decimals, as the iteration records are, in the language of the screen. Which metrics and groups to show, and the metric of the question table, are choices of the person.
- **One question side by side.** Opening a question shows, for each run, its answer (Markdown with math), the key facts hit, hit only by the lenient rule and missed (words and icons, not color alone), the gold papers cited out of those the set names, the citations, the passages the model read (collapsed) and the timings; with repeats, one selector serves every column. The key facts and gold papers come from `GET /sets/{name}/versions/{v}/items/{id}`; the scorer's `keys` records say which of them were found. A run's answer with an error shows the kind and message of the error.
- **State.** The server owns jobs, runs and scores (TanStack Query, `api.ts`); the compare screen's choices (metrics, group, filter, search, hidden runs, the open question, the repeat, the page) are one Zustand store in memory (`store.ts`), cleared when a score is opened. The rules that decide (is a job final, can it be cancelled, which score holds these runs, the average of the repeats, which keys were hit) are plain functions in `domain.ts` with their tests; `types.ts` reads the open objects of the API (`keys`, the item of a set) through guards.
- **Accessibility.** Every table has a caption and column headers, and a row header for its first column; a table wider than its card scrolls in a region a keyboard can focus. Progress is a polite live region; the log is not. Notices that are not errors use `role="status"`. The cancel question is a dialog with a title that Escape closes. Axe scans (WCAG 2.2 A and AA) run on the form, a running job, the cancel dialog, the partial runs, the starter, the results and the side by side, in light and in dark, and in Spanish.

`src/features/benchmarks/fixtures/captured.json` holds the real answers of the API for four runs of the demo set (the closed-book arm twice, the harness and the oracle, two repeats each) and a score of them with two pairs and a noise pair. The unit tests serve it through MSW (`src/test/benchmarks-api.ts`, which also has a small stand-in of the job lane for the tests of starting, cancelling and resuming). After a change in the API or in qa-bench, start the API in fake mode with no pause and run `pnpm capture:benchmarks http://127.0.0.1:8091` (`uv run research-api serve --fake --port 8091 --bench-pause 0`). `e2e/benchmarks.spec.ts` runs the acceptance checks B1 to B5 and B7 in the browser against the real API in fake mode as the seeded member `dani`: the start form and its limits, two runs never sharing the lane (the API is watched while they run), progress without a reload, cancel with its question, the partial run and the resume to the last answer (every question and repeat once), the score of two runs with a noise pair and every number of the comparison (the floor included) compared with what `GET /scores/{id}` returns, a double click on Start, Resume and Score that sends one request, the score of a cancelled run that is not opened for the results of the resumed one, the filter of disagreeing questions, and the side by side. The tests of this file run one after the other and each waits for a quiet lane first; the whole file takes about two minutes because the fake model takes a quarter of a second per answer.

## Sessions and routes

A route loader on `/` asks `/auth/me` through the query client. No session sends the visitor to `/login?next=<path>` (the path is kept only if it stays inside the app); a session that must change its password is held on `/login`, which then shows the change form instead of the sign-in form. The return path must be a plain path on this origin: a scheme, `//host`, a backslash or a control character (a browser drops a tab inside a URL, so `/<tab>/host` would read as `//host`) discards it. A 401 on any later request ends the session in the page: the cache is cleared and the user returns to `/login`. Signing out clears the cache and leaves only after the server has answered; if the call fails the page stays and a message says so. The session check itself is exempt from that rule (`EXPECTS_UNAUTHORIZED`), because its 401 is what the guards read.

After a navigation the page heading takes focus and sets the tab title (`useFocusPageTitle`); the login screen does the same when the sign-in form gives way to the password change and when it opens after signing out. A skip link jumps to the content.

Every screen sits under one error boundary inside the layout, so an error in a screen, or a lazy chunk that no longer exists after a new release, replaces that screen only. "Try again" asks the loaders again after a failed request and reloads the page after anything else.

## Languages and themes

The language is the saved choice (`localStorage` key `re.lang`), else the browser's first Spanish or English language, else Spanish. `es.json` and `en.json` must have the same keys and placeholders; a test fails otherwise. The terms of the data formats (`bare`, `harness`, `oracle`, `qset/1`, metric names) will stay as they are in both languages.

The theme is `system` (default), `light` or `dark` (key `re.theme`). `public/theme-init.js` sets the `dark` class before the first paint. It is an external file, not an inline script, so the API's Content-Security-Policy can stay at `script-src 'self'`. Every `localStorage` access is guarded: the app works with storage blocked.

## UI components

The components in `src/shared/ui` come from [shadcn/ui](https://ui.shadcn.com) (`radix-nova` style, Radix primitives, Tailwind CSS 4). `components.json` is set up for `pnpm dlx shadcn add <name>`. The CLI does not read the `@` alias from this project's split tsconfig, so it writes files under a folder literally named `@/` and imports `cn` from a package of that name; move the files into `src/shared/ui` and point the import at `@/shared/lib/utils` (the `cn` package it adds is not wanted).

## Dependencies

Versions are exact in `package.json` (`@types/node` included) and locked in `pnpm-lock.yaml`; `.nvmrc` names one Node release. `pnpm-workspace.yaml` sets `minimumReleaseAge` to 7 days, so a release younger than a week is never installed; a few packages are therefore one patch behind the newest (for example React Router 8.4.0, TanStack Query 5.104.3). TypeScript is 6.0.3: typescript-eslint does not support 7 yet. Two peer ranges are widened there on purpose, after checking that the tools run: `eslint-plugin-jsx-a11y` under ESLint 10 and `openapi-typescript` under TypeScript 6.

pnpm 12 runs no dependency build script unless it is allowed, and `onlyBuiltDependencies` is left unset on purpose: no package in the lock file declares an install script, so none can run code at install time.

`react-markdown`, `remark-math`, `rehype-katex` and `katex` are the Markdown and math stack of the scope. `rehype-katex` 7 and `micromark-extension-math` ask for `katex` ^0.16, which has a published advisory (fixed in 0.18.2), so `pnpm-workspace.yaml` overrides it: all three use `katex` 0.19.0.

New runtime dependencies need the lead's approval.

## Tests

Vitest runs the unit and component tests next to the code (the circuit screen has many of them: strict JSON, value parsing, number formatting, the gate list, the answer guards, every panel and every problem) (`*.test.ts(x)`): the client and its middlewares, error mapping, the theme and language rules, the forms, the router guards, the whole app on an in-memory router (sign-in, forced change, sign-out, session ending under an open page, navigation, theme and language switches, the status badge) and the translation parity. The Ask screen is tested on the real answers of the API: `pnpm capture:ask` records them (`src/features/ask/fixtures/captured.json`), MSW serves the papers and pages, and `src/test/event-source.ts` stands in for `EventSource` (jsdom has none) so a test plays the server's part event by event, including a connection that breaks. The Benchmarks screens are tested on the real answers of the API too (`pnpm capture:benchmarks`, see [The Benchmarks screens](#the-benchmarks-screens)). Playwright runs the smoke test (`e2e/smoke.spec.ts`, sign-in answered by the mock; the reads of the Benchmarks screen are answered with empty lists there, because the mock makes no real session), the real sign-in test (`e2e/real-api.spec.ts`), the Ask tests (`e2e/ask.spec.ts`: phases, citations, the paper panel, options, failures, a broken stream, cancel, history, Spanish, a narrow screen, with axe scans in both themes), the Benchmarks acceptance checks (`e2e/benchmarks.spec.ts`: B1 to B5 and B7) and the circuit screen's acceptance checks (`e2e/circuits.spec.ts`: C1 to C6 by hand, C7 as every LaTeX source of quantum-sim's bridge folder sent through the screen and compared with what the API says, the recorded answers, both themes, Spanish, a phone width, and 4 and 8 wire unitaries kept inside their cards at phone and desktop widths; it signs in against the real API first) and the question sets tests (`e2e/sets.spec.ts`) in Chromium against the production bundle, with an axe scan (WCAG 2.2 A and AA) of the login and forced-change pages in light and in dark (each page loads in its scheme) and of the app layout, also after a theme switch. The scan first waits for running transitions to end, so it never reads a color halfway through a fade; the focus moves after signing in and out are checked too.
